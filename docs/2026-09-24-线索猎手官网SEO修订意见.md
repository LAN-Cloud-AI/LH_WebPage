## 二、按优先级修订

### P0：让首屏重要文案首次绘制就可见

**已复现的现象：** Search Console 本次实时测试的移动端截图中，顶部标识之外的首屏大面积空白。实时测试 HTML，以及 Google 9 月 19 日已收录抓取的 HTML，均含有主标题和介绍文字，但相应元素在抓取快照中仍带有内联 opacity: 0。文字已经进入 DOM，因此不能把它等同于“Google 没抓到正文”，也不能直接断言它导致排名下降。

对应代码是 [src/sections/Hero.tsx 第 41–112 行](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/src/sections/Hero.tsx#L41-L112)：H1 两行、副文案、按钮及视觉区先透明，再延迟淡入；线上 JS 包含同一逻辑。减少动画设置下，H1 仍从透明状态开始。

实施要求：

1. 首页 H1、正文简介、品牌名和主要行动入口默认可见，不依赖计时器、滚动、IntersectionObserver 或动画完成才显示。可将这些 Motion 元素的 initial 改为 false，或采用同等的“首帧即显示”实现；装饰性位移与淡入仍可保留在不影响阅读的部分。
2. 检查 [Reveal.tsx](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/src/components/primitives/Reveal.tsx#L34-L75) 对各章节标题、正文的影响。搜索引擎不主动滚动时，SEO 关键内容应保持可见。
3. 三种语言页均按相同规则处理。不要针对 Googlebot User-Agent 输出专用内容。

验收：本地以移动视口抓取页面的“首次稳定帧”，H1 与简介可见；同时检查减少动画设置。上线后 Search Console 实时测试截图也能看到首屏文字，测试 HTML 中关键文案不再停留于 opacity: 0。Google 是否因此提升排名，需要单独观察，不能作为即时验收条件。

### P0：先对齐生产页面与仓库，再发布

当前线上英文页的 title、description、首屏品牌文案以 LeadsHunter 开头，而仓库 main 在 [src/content/identity.js 第 67–79 行](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/src/content/identity.js#L67-L79)对应内容以“线索猎手”开头。仓库的 [README 发布说明](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/README.md#L91-L103)显示官网由 Cloudflare Pages 手动直传；CI 只执行检查，不负责把 main 自动发布到生产。

实施要求：

1. 开工时重新核对远端 main、线上三语页面与当前 Pages 部署版本；保存三页现有 title、description、H1、canonical、hreflang、结构化数据、可见中英文品牌文案的对照。
2. 修订以当前生产实际文案为基准，确认哪些差异应保留，再修改源码。避免将 main 的旧文案直接覆盖到线上，尤其避免英文页的 LeadsHunter 品牌退化。
3. 提交时给出源码 commit、构建产物与拟部署版本的对应关系；发布后按线上响应重新验收，不以 CI 成功代替生产验收。

### P1：强化中英文品牌词的可见关联

简体首页目前的 title 和主标题只有“线索猎手”；LeadsHunter 虽见于英文页、导航及部分元数据，但在简体首屏不够突出。Google [建议把用户会搜索的词放在 title、主标题等显著位置](https://developers.google.com/search/docs/essentials)；[meta keywords 不参与 Google 网页排名](https://developers.google.com/search/docs/crawling-indexing/special-tags)。

建议将“线索猎手”和“LeadsHunter”在简体首页的 title、可见首屏文案与产品身份介绍中自然并列一次，例如“线索猎手 LeadsHunter｜从公开内容发现可跟进的销售线索”。英文页继续以 LeadsHunter 为主品牌，并保留必要的中文别名。同步核对公司站产品入口、产品介绍页、联系页及 App 下载页指向官网的链接文字，保持品牌称呼一致。避免堆砌关键词、重复品牌或无依据地增加产品能力宣传。

### P1：把三种语言的主要营销正文预渲染进初始 HTML

当前首次返回的 HTML 主要是简短 noscript 文案和空的 React 挂载点；详细介绍依赖客户端 JavaScript。Google 本次确实渲染出了正文，但[抓取、渲染、索引是不同阶段](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)，静态预渲染能提高公开营销页的可读性与稳定性。

实施时让 /、/en/、/zh-Hant/ 的初始 HTML 在不执行 JavaScript 的情况下也包含各自语言的真实 H1、主要介绍、关键章节与可抓取链接；交互再按现有方式增强。现有入口 [src/main.tsx](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/src/main.tsx#L11-L18)使用 createRoot，采用 React 预渲染时需同步处理 hydration，避免客户端接管时清空静态正文、产生两套重复正文或明显布局跳动。保留三页各自 canonical、hreflang、robots 指令、结构化数据和站点地图。

## 三、验证与交付要求

1. 在官网仓库完成修订，扩充 [SEO 校验脚本](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/scripts/verify-seo.mjs#L82-L115) 的断言：现有检查覆盖三语文件、hreflang 和 noscript，但未检查初始 HTML 中真正可见的品牌/H1/正文，也未检查首屏动画可见性。随后运行 build、seo:verify 与 check 流程；检查构建后的三语 HTML。所需脚本定义见 [package.json](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/package.json)。[三语生成脚本](https://github.com/LAN-Cloud-AI/LH_WebPage/blob/main/scripts/generate-locale-html.mjs#L268-L315)会在构建时回写 sitemap、robots 和 llms 文件，构建后应核对并解释工作树差异。
2. 用 JavaScript 关闭的浏览器或直接检查构建后的 HTML：三页的品牌、H1、主要内容和内链应仍可读取，且不是只写在 noscript 中。用 JavaScript 开启的移动浏览器检查首屏首次绘制与交互。
3. 比较修改前后的 title、description、canonical、hreflang、JSON-LD、robots.txt、sitemap.xml、语言切换和旧网址 301；保留 /en 与 /zh-Hant 到带斜杠目录的跳转及未知路径 404。修复首屏不能带来索引回退或语言串页。
4. 发布后核对实际线上三页、robots.txt、sitemap.xml 和重定向；再在 Search Console 对首页和英文页执行实时测试，保存截图及网址检查结果。页面更新后可请求重新索引，但“请求成功”不代表排名已恢复。
5. 用 Search Console 按“线索猎手”“LeadsHunter”及页面维度跟踪曝光、点击和排名，记录上线前基线，并在随后 2–4 周复盘。搜索结果首页抽检作为辅助证据，注明地区和日期。
6. 交付代码差异、测试结果、部署版本与线上复核记录；明确区分“代码修好”“已部署”“Google 已重新抓取”和“品牌词搜索改善”四个状态。

## 四、避免误判

- 已收录不等于品牌词一定排在前面；这次的核心现象是展示弱，而非抓取禁令。[Google 对网址检查的说明](https://support.google.com/webmasters/answer/12482179)
- Search Console 的实时测试用于即时排障，真正用于搜索结果的是 Google Index 视图中的上次抓取数据。本次两种视图都看到了透明的 H1，但无法量化它对排名的影响。
- 实时测试报告中 19 个资源有 1 个未加载，指向 stats.lancloudtech.com 的统计脚本被其 robots.txt 阻止；正文脚本和首页抓取成功，不应据此改动官网抓取策略。
- 某些普通自动客户端会收到 Cloudflare 403；Googlebot smartphone 与 Search Console 实时测试成功。判断 Google 访问能力应以 Google 自身报告和真实 Googlebot 日志为准。
